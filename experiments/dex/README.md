# Эксперимент: наш токен (Token-2022, налог 5%) на Meteora DAMM v2 и DLMM

Изолированный пакет (свои зависимости), чтобы не смешивать SDK Meteora с основным проектом.
Только тестовая сеть (devnet). Токен создаётся тот же, что и в проде: налог 5%, право менять налог убрано.

```bash
cd experiments/dex && npm install
export RPC=<devnet RPC>            # ключ провайдера хранится в переменной, не в файлах
npx ts-node damm.ts                # пул DAMM v2: создать, продать, купить
npx ts-node dlmm.ts                # пул DLMM: создать, добавить ликвидность, продать, купить
npx ts-node harvest.ts             # собрать налог со счетов обоих пулов
```

## Результат прогона (devnet, 2026-09-25)

| Что проверяли | DAMM v2 | DLMM |
|---|---|---|
| Пул с нашим токеном создаётся без разрешения Meteora (token badge) | да | да |
| Добавление ликвидности | да | да |
| Продажа токена за SOL | да | да |
| Покупка токена за SOL | да | да |

Налог ведёт себя одинаково в обоих пулах:
- **взнос ликвидности облагается 5%**: в пул реально попадает 95% (DAMM: из 10 млн осталось 500 000 удержанных; DLMM: из 5 млн удержано 250 000);
- **продажа**: 5% удерживается на счёте пула (по 50 000 с 1 млн проданных в DAMM, по 10 000 с 200 000 в DLMM);
- **покупка**: 5% удерживается на счёте покупателя (получает 95%);
- **налог со счетов пулов собирается** обычной инструкцией Token-2022 (`harvest`), которую может вызвать любой:
  бот сбора налога обязан включать в список счета пулов (vault/reserve), а не только счета людей.

## Чего этот прогон НЕ доказывает

- Поведение на **mainnet** (правила Meteora могут отличаться; перед запуском проверить малой суммой).
- Поддержку токена с налогом в **агрегаторах** (Jupiter и др.) и предупреждения кошельков.
- Влияние налога на арбитраж и цену; точность котировок пулов с налогом не сверялась.
- Какой пул лучше для запуска: это стратегия ликвидности и решение владельца, а не техническая необходимость.
